# FilterBridge v0.2.0

**Status:** published to npm on 2026-08-15. The per-package `CHANGELOG.md` files were generated
from the changesets by `pnpm changeset version`; this note is the narrative version of the same
content and is what the GitHub Release body is taken from.

Post-release hardening ([Sprint 0](../sprints/sprint-0/README.md)). Correctness defects found in
published `0.1.0` code, two API gaps closed, per-filter defaults added, and the test suite rebuilt
so that the next defects are found by the suite instead of by hand.

---

### Why `@filterbridge/tanstack` and `@filterbridge/next` moved too

They have no functional change in this release. The five packages are a `fixed` group in
`.changeset/config.json`, so they always version together, and their `CHANGELOG.md` entries for
`0.2.0` say only "Updated dependencies".

That is deliberate. The alternative — letting each package drift to its own number — means asking
every user which combination of five versions is compatible, for a set of packages that are
developed, tested and released as one unit. One version across the group is the answer to that
question. The cost is a version bump that reads as empty for a package you happen to be looking at
in isolation, and this note is here so that reads as policy rather than as a mistake.

Both adapters do inherit the `@filterbridge/core` changes below, since they parse and serialize
through it.

### Why `0.2.0` and not `0.1.1`

The sprint set out to be a bug-fix release. It added public API in three packages — per-filter
defaults, `syncState` + `usePopstateSync`, and `resetToInitial()` — and new API is not a patch. The
bug fixes ride along in the same release.

## Behavior changes to read before upgrading

None of these require code changes, but each one changes what an existing call produces. They are
listed first, not buried under "fixed", because a reader should be able to see them without opening
the diff.

| Change                                               | Before                                                    | Now                                                                            |
| ---------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Serialization validates against the schema           | `toSearchParams(s, { status: 'bogus' })` → `status=bogus` | omitted, with a dev-only `console.warn`                                        |
| Whitespace and empty values are normalized on output | `{ search: '   ' }` → `search=+++`                        | omitted; surviving values are trimmed                                          |
| Non-finite numbers are rejected on both sides        | `{ min: NaN }` → `amountMin=NaN`, DTO `{"min":null}`      | omitted; `JSON.stringify(toQueryDto(...))` can never emit `null`               |
| `toQueryDto` type-checks `boolean`                   | `{ active: 'true' }` kept as a string                     | omitted, matching `toSearchParams`                                             |
| `parseFilters` rejects `Infinity`                    | `amountMin=Infinity` entered state                        | ignored — `parseFloat('Infinity')` is `Infinity`, and `1e999` is the same case |
| **`toQueryDto` carries defaults**                    | a filter at its default was omitted from the DTO          | included — see below                                                           |
| **`clear()` on a defaulted filter**                  | removed the key                                           | returns it to its default                                                      |
| **`activeFilterCount`**                              | counted every key in state                                | does not count a filter sitting at its default                                 |

Every value affected by the first five was already broken end to end — it did not survive a re-parse
or was not representable in JSON — so no correct integration depended on the old output. The last
three concern defaults, which are new in this release, so nothing published depends on them either.

## New

### Per-filter defaults — `@filterbridge/core`

`select`, `multiSelect` and `boolean` take an optional configuration object as their last argument:

```ts
const orderFilters = defineFilters({
  status: select(['pending', 'paid', 'failed'] as const, { default: 'pending' }),
  archived: boolean({ default: false }),
})

getDefaultFilterState(orderFilters)
// { status: 'pending', archived: false }
```

A filter at its default emits no query param, and `parseFilters` puts the default back when the
param is missing or invalid — so the shortest URL is also the correct one.

**Only filters whose value space is a fixed, enumerable set accept a default.** `text()`,
`dateRange()` and `numberRange()` take no configuration at all, and passing one is a type error.
Clearing a filter returns it to its default, which is coherent for a discrete choice and hostile for
continuous editing: a text or number input would repopulate itself while the user was still
backspacing through it. A literal date default fails for a different reason — `'2026-01-01'` means
something else every month. Express those as discrete choices instead:

```ts
period: select(['7d', '30d', '90d'], { default: '30d' })
```

`select` and `multiSelect` validate their default against `options` at schema definition and throw
if it does not belong. This is the one place core throws: a default is static configuration, so a
typo fails identically on every run.

Also exported: `getDefaultFilterState(schema)`, `isAtDefault(filter, value)`, `FilterConfig<T>`, and
the `DateRangeValue` / `NumberRangeValue` state shapes.

#### The DTO carries defaults; the URL does not

The two outputs deliberately carry different bytes, and the reason is what happens on the other side.

Omitting a default from the URL is compression with a guaranteed decompressor: `parseFilters` reads
it back and restores the default. Nothing is lost.

The DTO has no such closure. It leaves for a backend that does not run FilterBridge and cannot know
the schema, so an omitted default is loss. A page sitting at `status: 'paid'` rendered "paid" in the
control, serialized to an empty URL, and handed the backend `{}` — which returned every row.

```ts
const state = parseFilters(schema, new URLSearchParams(''))
// { status: 'paid' } — the page is filtering

toSearchParams(schema, state).toString() // '' — safe, parseFilters restores it
toQueryDto(schema, state) // { status: 'paid' } — the backend is told
```

`toQueryDto` applies the same fallback rule as `parseFilters` — absent, empty or invalid becomes the
default — so `toQueryDto(state)` always equals
`toQueryDto(parseFilters(schema, toSearchParams(schema, state)))`.

### Back/forward navigation — `@filterbridge/react`, `@filterbridge/browser`

```tsx
const bridge = useFilterBridge(orderFilters, {
  initialState: parseFiltersFromUrl(orderFilters),
  onChange: (state) => pushUrlFilters(orderFilters, state),
})

usePopstateSync(orderFilters, bridge.syncState)
```

- **`useFilterBridge().syncState(state)`** replaces the whole state and deliberately does **not**
  fire `onChange`. That is the invariant that makes the pairing safe: `onChange` writes to the URL,
  and `syncState` is called _because_ the URL already changed.
- **`usePopstateSync(schema, onState, options?)`** lives in a new `@filterbridge/browser/react`
  entry point. React is an **optional** peer dependency and only that subpath imports it, so
  `@filterbridge/browser` stays importable in plain Node or any non-React app.

Back/forward only has somewhere to go if filter changes are written with `pushUrlFilters`;
`replaceUrlFilters` keeps a single history entry.

### `resetToInitial()` — `@filterbridge/react`

`reset()` keeps its published meaning. `resetToInitial()` restores the `initialState` captured on
the first render, so the capability the spec described now exists under its own name.

### Hook state is always a state some URL parses to

`useFilterBridge` layers every write over the schema defaults. Without it, `{}` is reachable through
`reset()`, `clear()`, `set(key, undefined)` and `syncState({})`, and `{}` is not expressible as a
query string — the UI would show a filter as cleared while the URL and the DTO both read it as its
default.

- `clear(key)` on a filter **with** a default returns it to that default. On one without, it removes
  the key, exactly as before.
- `reset()` returns to the page's baseline: `{}` without defaults, the defaults with them. There is
  no separate `resetToDefaults()` — that is what `reset()` now is.

Schemas that declare no defaults are byte-identical to `0.1.0` in parsing, serialization, DTO output
and hook behavior.

## Fixed

- **Repeated query params were silently dropped.** `normalizeInput` flattened `URLSearchParams` with
  `forEach`, so `tags=a&tags=b` parsed to `['b']`. It now collects every value with `getAll`, and
  mixed forms work: `tags=a,b&tags=c` → `['a', 'b', 'c']`. Scalar filters take the first occurrence,
  matching `@filterbridge/next` — which closes a hydration mismatch where the two packages
  disagreed about the same URL.
- **`NaN` and `Infinity` leaked into URLs and DTOs**, on the way out and on the way in.
- **Serialization did not validate against the schema.** The membership rule now lives in one module
  used by the parser and both serializers, so the three directions cannot drift apart again.
- **Empty and whitespace values leaked into output.** `toQueryDto` now rebuilds a `dateRange` from
  its surviving sides instead of passing the object through, so an empty side never reaches a
  backend as `''`.
- **`toQueryDto` never type-checked `boolean`**, so `{ active: 'true' }` was dropped from the URL and
  kept in the DTO as a string. Found by the DTO-parity property test, not by reading the code.
- **`cleanFilterState`** (`@filterbridge/react`) treats a non-finite number, and a range whose sides
  are all empty strings, as empty.
- **Three defects in the demo:** a footer link to a repository that does not exist; an Archived
  checkbox that could never return to "not filtering" once touched, now a three-option select; and
  form labels with no association to their controls, so every field routed through `FieldGroup` had
  no accessible name.

## Infrastructure

Not part of the published packages, but the reason to trust this release more than the last one.

- **Continuous integration**, on push to `main` and on every pull request: `install → build → lint →
typecheck → test` on Node 18/20/22 on Linux and Node 20 on Windows, plus a demo build and a
  changeset check. Nothing had ever run automatically on this repository before.
- **`packageManager` is pinned**, so CI, local development and the deploy all resolve the same pnpm
  instead of whatever each platform picks by heuristic.
- **The test suite resolves `@filterbridge/*` to source**, not to each package's `dist/`. It used to
  report on whatever was built last, which is how a broken `syncState` invariant passed `pnpm test`
  while failing the same test run directly. `.smoke/` covers the published artifact instead, by
  installing the real tarballs and exercising the export map in ESM and CJS.
- **The demo's version badge** is injected from `packages/core/package.json` at build time rather
  than maintained by hand.

## Testing

The `0.1.0` suite passed 299 tests and caught none of the P0 defects above: it was extensive but
example-based, checking inputs the implementation was written to handle.

- **Round-trip property tests** — 500 generated states and 500 generated query strings per schema,
  against a schema with defaults and one without. Values are generated deliberately _outside_ the
  schema: invalid options, non-finite numbers, whitespace strings, wrong types, repeated params,
  foreign keys. The properties asserted are that `parse ∘ serialize` is a fixed point, that
  `toQueryDto` agrees with the URL, that every DTO survives `JSON.stringify` unchanged, and that no
  key outside the schema is ever emitted. The generator is hand-written — a seeded LCG, roughly 40
  lines — so the dependency count stays at zero.
- **Hook state invariant** — 200 generated sequences of `set` / `clear` / `reset` / `setMany` /
  `syncState`, asserting after every operation that some URL parses to the resulting state.
- **Named regression tests** — `sprint-0-regressions.test.ts` carries the exact reproduction from
  each task file, so a regression names the bug it reintroduced instead of failing an opaque
  generated case.
- **Cross-package parity** — `parseFilters` and `parseNextSearchParams` must agree on 300 generated
  URLs, in both input shapes Next.js can hand a page, on a schema with defaults and one without.
- **Verified by reverting** — every fix in this release was reverted individually and the suite
  confirmed red. Three of the defects were found _by_ the new property tests rather than by hand.

Current: **538 tests / 28 files**, green on Node 18/20/22 on Linux and Node 20 on Windows.

## Known limitations

- No custom key suffixes for `dateRange` / `numberRange`
- No date string validation beyond accepting non-empty strings
- `filterBridgeFilterFns.dateRange` uses lexicographic ISO string comparison — no timezone support
- `createNextFilterHref` deduplicates repeated non-filter params
- `parseFilters` is lenient about trailing garbage in numbers (`amountMin=100abc` parses as `100`)
- `InferFilterState` types every field as optional, including filters that declare a default and can
  therefore never be absent. Deferred to `v1.0` — see
  [ADR-002](../decisions/002-default-values.md)

## Upgrade

```bash
npm install @filterbridge/core@0.2.0
```

No code changes are required unless you pass a default to `text()`, `dateRange()` or
`numberRange()` — those builders no longer accept one, and the compiler will tell you. Read the
behavior-change table above if you consume `toQueryDto` output directly, rely on `activeFilterCount`,
or pass unvalidated state to the serializers.
