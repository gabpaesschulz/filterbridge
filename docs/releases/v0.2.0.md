# FilterBridge v0.2.0

**Status:** draft — not published yet. Written from the changesets in `.changeset/`; run
`pnpm changeset version` to generate the per-package `CHANGELOG.md` from the same source.

Post-release hardening ([Sprint 0](../sprints/sprint-0/README.md)). Four correctness defects found
in published `0.1.0` code, two API gaps closed, and the test suite rebuilt so that the next four are
found by the suite instead of by hand.

### Why `0.2.0` and not `0.1.1`

The sprint set out to be a bug-fix release. Three of its changesets are `minor` — per-filter
defaults, `syncState` + `usePopstateSync`, and `resetToInitial()` — and new public API is not a
patch. The bug fixes ride along in the same release.

## New

### Per-filter defaults — `@filterbridge/core`

Every filter factory takes an optional config object as its last argument:

```ts
const orderFilters = defineFilters({
  status: select(['pending', 'paid', 'failed'] as const, { default: 'pending' }),
  amount: numberRange({ default: { min: 0 } }),
})

getDefaultFilterState(orderFilters)
// { status: 'pending', amount: { min: 0 } }
```

A filter at its default emits no query param, and `parseFilters` puts the default back when the
param is missing or invalid — so the shortest URL is also the correct one.

### Back/forward navigation — `@filterbridge/react`, `@filterbridge/browser`

```tsx
const bridge = useFilterBridge(orderFilters, {
  initialState: parseFiltersFromUrl(orderFilters),
  onChange: (state) => pushUrlFilters(orderFilters, state),
})

usePopstateSync(orderFilters, bridge.syncState)
```

`syncState(state)` replaces hook state from outside and deliberately does **not** fire `onChange` —
otherwise every Back press would re-push the state the user just navigated away from.
`usePopstateSync` ships from the new `@filterbridge/browser/react` entry point; React is an
*optional* peer dependency, so the root entry stays importable without React.

### `resetToInitial()` — `@filterbridge/react`

`reset()` clears everything and always has. The capability the spec described under that name now
exists under its own: `resetToInitial()` restores the `initialState` captured at mount.

## Fixed

- **Repeated query params were silently dropped.** `tags=a&tags=b` parsed to `['b']` — the last
  occurrence of a key overwrote the rest. `multiSelect` now accepts repeated params,
  comma-separated values, and any mix of the two. `@filterbridge/next` already did this, so the same URL parsed by two
  FilterBridge packages produced two different states; there is now a cross-package test asserting
  they agree.
- **`NaN` and `Infinity` leaked into URLs and DTOs.** `{ amount: { min: NaN } }` produced
  `amountMin=NaN` and `{"min":null}` over the wire. Both serializers and the parser now guard with
  `Number.isFinite`.
- **Serialization did not validate against the schema.** A `select` value outside a filter's
  `options` went straight into the URL and the DTO, then vanished on re-parse. Membership is now
  checked in all three directions from one shared rule, with a dev-only `console.warn` when a value
  is dropped. Serialization never throws — it runs inside a React render path.
- **Empty and whitespace values leaked into output.** `{ search: '   ' }` produced `search=+++` and
  `{"search":"   "}`. Text is trimmed on the way out as it already was on the way in, and a range
  side that is an empty string is dropped rather than sent to a backend as `''`.
- **`toQueryDto` did not type-check `boolean`.** `{ active: 'true' }` was dropped from the URL and
  kept in the DTO as a string.
- **Demo app** — the three defects visible on the deployed demo are fixed (not published to npm).

### Behavior changes to read before upgrading

These narrow what the serializers accept. Every affected value was already broken end-to-end — it
did not survive a URL round trip, or was not representable in JSON — so no correct integration
depends on the old output. Code reading `toQueryDto` output directly will see keys disappear:

| Input | `0.1.0` output | `0.2.0` output |
|-------|----------------|----------------|
| `select` value outside `options` | in URL and DTO | omitted, dev warning |
| `multiSelect` entry outside `options` | in URL and DTO | omitted, dev warning |
| whitespace-only `text` | `search=+++`, `{"search":"   "}` | omitted |
| `dateRange` side as `''` | `{"from":""}` | omitted |
| non-finite `numberRange` side | `amountMin=NaN`, `{"min":null}` | omitted |
| non-boolean in a `boolean` slot | kept in DTO | omitted |
| `amountMin=Infinity` in an incoming URL | parsed to `Infinity` | ignored |

A filter at its configured default now also emits no param. If you relied on every filter appearing
in the query string, declare no defaults.

## Testing

The `0.1.0` suite passed 299 tests and caught none of the four P0 defects above: it was extensive
but example-based, checking inputs the implementation was written to handle.

- **Round-trip property tests** — 500 generated states and 500 generated query strings per schema,
  run against a schema with defaults and one without. Values are generated deliberately *outside*
  the schema: invalid options, non-finite numbers, whitespace strings, wrong types, repeated params,
  foreign keys. The properties asserted are that `parse ∘ serialize` is a fixed point, that
  `toQueryDto` agrees with the URL, that every DTO survives `JSON.stringify` unchanged, and that no
  key outside the schema is ever emitted. The generator is hand-written (a seeded LCG, ~40 lines) —
  `fast-check` was considered and skipped to keep the dependency count at zero.
- **Named regression tests** — `sprint-0-regressions.test.ts` carries the exact reproduction from
  each task file, so a regression names the bug it reintroduced.
- **Cross-package parity** — `parseFilters` and `parseNextSearchParams` are asserted to agree on 300
  generated URLs, in both input shapes Next.js can hand a page.
- **Verified by reverting** — each fix was reverted one at a time and the suite confirmed red. Two
  of the defects this release fixes were found *by* the new property tests, not by hand.

Current: **507 tests / 28 files**, plus `lint`, `typecheck` and `build` on Node 18/20/22 (Linux) and
Node 20 (Windows) in CI, with a demo build and a changeset check on every pull request.

## Known limitations

- No custom key suffixes for `dateRange` / `numberRange`
- No date string validation beyond accepting non-empty strings
- `filterBridgeFilterFns.dateRange` uses lexicographic ISO string comparison — no timezone support
- `createNextFilterHref` deduplicates repeated non-filter params
- `parseFilters` is lenient about trailing garbage in numbers (`amountMin=100abc` parses as `100`)

## Upgrade

```bash
npm install @filterbridge/core@0.2.0
```

No code changes are required. Read the behavior-change table above if you consume `toQueryDto`
output directly or if you pass unvalidated state to the serializers.
