## Highlights

- **Schema-first API** — declare filters once with `defineFilters()` and derive parsing, URL serialization, and backend DTOs from that single definition.
- **Six filter types** — `text`, `select`, `multiSelect`, `boolean`, `dateRange`, `numberRange`.
- **TypeScript inference** — full state type inferred from schema, including literal union types for `select` and `multiSelect`.
- **Zero framework dependency in core** — `@filterbridge/core` has no React dependency and works in any environment.
- **Browser URL sync** — `@filterbridge/browser` provides `parseFiltersFromUrl`, `createFilterUrl`, `pushUrlFilters`, and `replaceUrlFilters`.
- **TanStack Table adapter** — `@filterbridge/tanstack` converts between FilterBridge state and TanStack `columnFilters`, with optional client-side filter functions.
- **Next.js App Router adapter** — `@filterbridge/next` parses server component `searchParams` and builds navigable hrefs. No Next.js runtime dependency.
- **299 automated tests** — core parsing, serialization, DTO conversion, React hook behavior, browser URL helpers, TanStack adapter, and Next.js adapter.

## What works today

### `@filterbridge/core`

- `defineFilters(schema)` — creates a typed filter schema
- `parseFilters(schema, input)` — parses `Record<string, unknown>` or `URLSearchParams`
- `toSearchParams(schema, state)` — deterministic URL serialization
- `toQueryDto(schema, state)` — backend-friendly DTO (strips empty values)
- `getDefaultFilterState(schema)` — the state a schema starts from, for filters that declare a `default`
- `InferFilterState<TSchema>` — full TypeScript inference from schema

### `@filterbridge/react`

- `useFilterBridge(schema, options?)` — React hook with `state`, `set`, `setMany`, `clear`, `reset`, `syncState`
- `hasActiveFilters`, `activeFilterCount` — derived filter state
- `toQueryDto()`, `toSearchParams()` — methods on hook return value
- Automatic empty-value cleanup

### `@filterbridge/browser`

- `parseFiltersFromUrl(schema, input?)` — reads from `window.location.search` or accepts URL/string/URLSearchParams
- `createFilterUrl(schema, state, options?)` — builds a URL path string
- `replaceUrlFilters(schema, state)` — `history.replaceState`
- `pushUrlFilters(schema, state)` — `history.pushState`
- `getFilterParamKeys(schema)` — returns all URL keys for a schema
- `usePopstateSync(schema, onState)` — from `@filterbridge/browser/react`; restores filter state on back/forward
- SSR-safe (no-op when `window` is not available)

### `@filterbridge/tanstack`

- `toTanStackColumnFilters(schema, state, options?)` — FilterBridge state → TanStack `columnFilters`
- `fromTanStackColumnFilters(schema, columnFilters, options?)` — TanStack `columnFilters` → FilterBridge state
- `filterBridgeFilterFns` — client-side filter functions for `text`, `select`, `multiSelect`, `boolean`, `dateRange`, `numberRange`
- `columnIds` remapping option

### `@filterbridge/next`

- `parseNextSearchParams(schema, searchParams?)` — sync parsing from Next.js searchParams
- `parseNextSearchParamsAsync(schema, searchParams?)` — async variant for Next.js 15+
- `normalizeNextSearchParams(schema, searchParams?)` — low-level normalization
- `createNextFilterHref(schema, state, options?)` — builds href string for `<Link>` or `router.push()`
- No Next.js runtime dependency

## Known limitations at the time of this release

- No custom key suffixes for `dateRange` / `numberRange`
- No date string validation beyond accepting non-empty strings
- `filterBridgeFilterFns.dateRange` uses lexicographic ISO string comparison — no timezone support
- `createNextFilterHref` deduplicates repeated non-filter params

Removed in `0.2.0`: repeated query params are now parsed, `popstate` is handled, and filters can
declare defaults.

```bash
npm install @filterbridge/browser # optional browser URL sync
npm install @filterbridge/tanstack @tanstack/react-table # optional TanStack adapter
npm install @filterbridge/next    # optional Next.js adapter
```

## Note on stability

This is an experimental release. The core concepts are solid and the API is usable, but breaking changes may happen before `v1.0`. If you use FilterBridge in production, pin your version.
