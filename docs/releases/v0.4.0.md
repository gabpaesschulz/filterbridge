# FilterBridge v0.4.0

**Status:** versioned and verified; `npm publish` is the maintainer's step. The per-package
`CHANGELOG.md` files were generated from the changesets by `pnpm changeset version`; this note is
the narrative version of the same content and is what the GitHub Release body is taken from.

The hook's contract with React ([Sprint 2](../sprints/sprint-2/README.md)). One defect fixed that
`0.3.1` shipped knowingly, one API addition that finishes what `0.3.1` started, and a React major
the packages have always claimed to support and never once ran.

---

## The short version

**You can navigate from `onChange` now.** `router.push` / `router.replace` in a Next.js `onChange`
no longer logs `Cannot update a component while rendering a different component`, and the
`queueMicrotask` workaround the `0.3.1` guide told you to write is no longer needed.

**Scalar filters take a URL param key.** `text({ key: 'q' })` serializes to `?q=`.

### Why a minor

New public API — `key` on four builders, plus `scalarParamKey`, `ParamKeyConfig` and `TextConfig` —
and one observable behavior change in `useFilterBridge`. In `0.x`, minor is the conventional signal
for new API surface.

## Fixed: `onChange` no longer fires during the render phase

`useFilterBridge` called `onChange` from inside its `setState` updater. React runs updaters during
the render phase and requires them to be pure, so the callback most people use to write the URL was
running somewhere React does not allow side effects.

The next state is now computed in the event handler that triggered it, and `onChange` is called
there.

**What you get:**

```ts
// 0.3.1 — logs "Cannot update a component (Router) while rendering
// a different component (InvoicesClient)"
onChange(nextState) {
  const href = createNextFilterHref(schema, nextState, { pathname, searchParams })
  queueMicrotask(() => router.push(href, { scroll: false })) // the workaround
}

// 0.4.0
onChange(nextState) {
  const href = createNextFilterHref(schema, nextState, { pathname, searchParams })
  router.push(href, { scroll: false })
}
```

**What changes that you can observe:** under `<React.StrictMode>` — on by default in
`create-next-app` and Vite's React template — `onChange` fired **twice** per state change in
development. It now fires once. Nothing else moves: the callback still fires synchronously as part
of the action, with the same argument, before the re-render.

`apps/demo` never warned, which is how this survived three releases: it writes to `window.history`
in `onChange`, and that is not a React state update. `@filterbridge/browser`'s `pushUrlFilters` and
`replaceUrlFilters` were never affected for the same reason.

The reasoning, the two options rejected, and what the chosen one costs are in
[ADR-006](../decisions/006-onchange-timing.md).

## New: custom URL param key for the scalar filters

`0.3.1` gave `dateRange` and `numberRange` a `keys` option — plural, because a range occupies two
params, and deliberately plural so that `key` would be free for the filters that occupy one. It is
free no longer:

```ts
const filters = defineFilters({
  search: text({ key: 'q' }),
  status: select(['pending', 'paid'] as const, { key: 'st', default: 'paid' }),
  tags: multiSelect(['urgent', 'review'] as const, { key: 'labels' }),
  archived: boolean({ key: 'is_archived' }),
  createdAt: dateRange({ keys: { from: 'created_after' } }),
})

toSearchParams(filters, { search: 'invoice', archived: false }).toString()
// q=invoice&is_archived=false
```

`key` for one param, `keys` for two — the singular and the plural are the whole convention.

Four things worth knowing:

- **State and DTO stay keyed by filter name.** `key` renames the URL param, not the field.
  `state.search` is `search` whatever the query string says, and so is `toQueryDto(...).search`.
  The column id `@filterbridge/tanstack` uses is likewise untouched; it has its own `columnIds`.
- **A key replaces the name; it is not an alias.** Once `search` writes `q`, a URL carrying
  `search=invoice` parses to nothing. Anything else would make a rename unobservable and quietly
  keep old bookmarks pointing at a param the schema no longer claims.
- **Collisions throw at definition time**, through the check `0.3.1` added. Renaming is a real
  escape hatch, so `{ q: text({ key: 'query' }), search: text({ key: 'q' }) }` is fine.
- **`text` accepts `{ key }` and still refuses `{ default }`** as a type error, per
  [ADR-002 §4](../decisions/002-default-values.md).

`@filterbridge/browser` and `@filterbridge/next` follow the override with no API change of their
own.

### The refactor underneath it

`packages/core/src/param-keys.ts` opens by calling itself "the one place in the repository that
knows how a filter name becomes a URL param key". That was true for the two range kinds. The four
scalar kinds still indexed the input by filter name directly, in three files — correct only because
for a scalar the derivation happened to be the identity.

Routing them through the same module landed as its own commit with no behavior change, guarded by
798 tests passing unmodified, before the option that would have made three copies wrong. It is the
same shape as the `0.3.1` collapse, and for the same reason: duplicated key knowledge is what let
`core` and `next` disagree about one URL in `0.1.0`.

`core` gains `scalarParamKey`, exported for the reason `dateRangeParamKeys` is — `@filterbridge/next`
needs it inside its own `switch`.

## Tested: React 19

`@filterbridge/react` and `@filterbridge/browser` have declared `react: >=18` since `0.1.0`, and the
suite only ever ran `18.3.x`. Both suites now run twice, once per major, as separate vitest projects
over the same test files.

**No library change was needed** — both packages already worked on React 19. What changed is that
the peer range is now checked rather than declared, and a React 19 regression would fail a pull
request instead of reaching a user.

Strict Mode is also in the suite for the first time, which is what makes "`onChange` fires exactly
once" assertable at all.

## Upgrading

`pnpm add @filterbridge/core@0.4.0 @filterbridge/react@0.4.0` — and the same for `browser`,
`tanstack` and `next` if you use them. They are a fixed group; keep them on one version.

Nothing is removed or renamed, and no existing schema changes meaning. Two things to do:

1. **Delete the `queueMicrotask` wrapper** if you copied it from the `0.3.1` Next.js guide.
   `router.push(href)` in `onChange` is correct now, and the wrapper is a needless tick of delay.
2. **If you counted `onChange` calls in a Strict Mode dev environment**, expect half as many. This
   is the fix, not a regression.
