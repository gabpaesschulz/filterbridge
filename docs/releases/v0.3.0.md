### Why `0.3.0` and not `0.2.1`

New public API in two builders, four new exported functions in `core`, and one behavior change that
turns a previously-silent schema mistake into a throw. In `0.x`, minor is the conventional signal
for new API surface.

## Behavior change to read before upgrading

One, and it is the only one.

### `defineFilters` throws on a duplicate URL param key

```ts
defineFilters({
  createdAtFrom: text(),
  createdAt: dateRange(), // also writes createdAtFrom
})
// Error: [filterbridge] defineFilters(): filters "createdAtFrom" and "createdAt"
// both use the URL param "createdAtFrom". Rename one, or give it an explicit
// keys override.
```

This is reachable **without** any of the new API, and it was reachable in `0.2.0` — where
`toSearchParams` silently let the last writer win, so one of the two filters round-tripped to a value
it never held. Such a schema was never working. It did not throw before and it does now.

The fix is to rename one filter, or to give one an explicit `keys` override. It throws rather than
warns for the reason [ADR-002](../decisions/002-default-values.md) gives for defaults: a schema is
static configuration evaluated once at module load, so a collision is a source-level mistake that
fails identically on every run — not untrusted input arriving in a render path.

**A schema with no collision is unaffected, and a schema with no `keys` produces byte-identical URLs
to `0.2.0`.** That was an acceptance criterion, verified by the 538 tests from `0.2.0` passing
without a single edit.

## New

### Custom URL keys for `dateRange` and `numberRange` — `@filterbridge/core`

A range filter writes two params, named after the filter. That is fine while FilterBridge owns both
ends of the URL. It stops being fine the moment the query string is read by something that already
has an opinion about its parameter names — an existing REST endpoint, a URL scheme that predates the
library, a backend shared with a non-JavaScript client. The only previous answer was renaming params
by hand after `toSearchParams()`, which reintroduces exactly the glue code the library exists to
delete.

```ts
const filters = defineFilters({
  createdAt: dateRange({ keys: { from: 'created_after', to: 'created_before' } }),
  amount: numberRange({ keys: { min: 'min_cents' } }),
})

toSearchParams(filters, {
  createdAt: { from: '2026-01-01', to: '2026-01-31' },
  amount: { min: 100, max: 500 },
}).toString()
// created_after=2026-01-01&created_before=2026-01-31&min_cents=100&amountMax=500
```

- **Either side may be given alone.** `amount` above overrides only `min`; `max` stays `amountMax`.
  Half-configured is a real state — an API that renamed one param and not the other — and a mixed URL
  is a better outcome than a builder that throws for not having been told something it could derive.
- **The key replaces the whole param name, not a suffix.** That is what makes `created_after`
  reachable from a filter named `createdAt`; a suffix override could only ever produce
  `createdAt_after`.
- **`toQueryDto` is unaffected.** The DTO stays keyed by filter name, with ranges nested as
  `{ from, to }` / `{ min, max }`. A custom key is a URL concern; renaming JSON properties for a
  backend is a different problem and out of scope. There is a test asserting this, because "I set
  `keys` and my DTO did not change" is the question it will generate.

The option is named `keys` and not `key` on purpose, leaving `key: string` free for a future scalar
override — `text()` serializing to `q` — which can then be added without renaming anything.

### One place derives URL param keys

This is the part worth more than the feature.

Before this release the `From` / `To` / `Min` / `Max` rule was spelled out **independently in four
places**: `parseFilters`, `toSearchParams`, `@filterbridge/browser`'s `getFilterParamKeys`, and
`@filterbridge/next`'s normalization. That is the same duplicated-knowledge shape that let `core` and
`next` disagree about repeated query params before `0.2.0` — one URL, two states, silent data loss.
Adding a per-filter override to four copies would have made it worse, so the option and the collapse
landed together.

Derivation now lives in `packages/core/src/param-keys.ts` and nowhere else, exported as:

```ts
import {
  dateRangeParamKeys, // (name, filter) => { from, to }
  filterParamKeys, // (name, filter) => string[]
  getFilterParamKeys, // (schema)      => string[]
  numberRangeParamKeys, // (name, filter) => { min, max }
} from '@filterbridge/core'
```

`getFilterParamKeys` still exports from `@filterbridge/browser` with an unchanged name, signature and
return type — the implementation moved, the export did not. It reports custom keys, which is what
lets `createFilterUrl` strip a stale one; a key it failed to report would sit in the URL forever.

`@filterbridge/next` reads the same derivation, asserted by new cases in its cross-package parity
suite: a server parse and a client parse of the same custom-keyed URL produce the same state.

New exported types: `DateRangeConfig`, `NumberRangeConfig`, `DateRangeKeys`, `NumberRangeKeys`.

## Documentation and examples

### A Next.js App Router example that runs

[`examples/next-app-router`](../../examples/next-app-router) is a Next.js 15 application: a server
component parsing `searchParams`, a client component holding the state, a filter with a `default` so
the URL-omits-but-DTO-carries rule is visible, and a non-filter param that survives a filter change.

It sits **outside** the pnpm workspace and installs with `npm`, pinned to published FilterBridge
versions, so it costs nothing to anyone who never opens it — and CI does not build it, which is the
accepted cost.

Before this, `@filterbridge/next`'s entire correctness argument was unit tests plus a 220-line guide
of snippets that had never been executed. Executing them found two false claims:

**`router.replace` leaves no history to go back to.** The guide navigated with `replace`, which
overwrites the current entry, so the app had exactly one and pressing Back left it entirely.

**A server re-render does not reach the filter controls.** With `push` in place, Back updated the URL
and the server-rendered rows and left every input where it was. That is correct behavior from
`useFilterBridge`, which captures `initialState` once by design, but it makes the guide's claim —
"re-parses and re-initializes state correctly" — false, and a half-updated page is worse than either
half being wrong alone.

Both are corrected. The pattern is `router.push` plus `usePopstateSync(schema, bridge.syncState)`
from `@filterbridge/browser/react` — the pair
[ADR-004](../decisions/004-external-state-sync.md) introduced for exactly this.

### The demo meets WCAG AA

25 colour-contrast violations, all pre-existing, are gone. `--color-muted` went from 4.43:1 to
5.62:1 on the page background — it was missing the threshold by 0.07, which is the margin that
proves nobody had measured it. Status pills moved from white on a saturated fill (2.54–3.30:1) to
dark text on a light tint (6.10–9.37:1); no hue at those lightnesses reaches AA against white
without going dark enough to stop reading as a status colour.

`pnpm demo:a11y` is new: Playwright plus axe-core with `color-contrast` **enabled**, against the
running demo. The committed jsdom suite must keep that rule disabled — jsdom has no layout engine —
so this is the only thing that can catch the class of bug. It is run by hand, not in CI.

## Known issue shipping unfixed

**`useFilterBridge` fires `onChange` during the render phase.** It calls the callback from inside its
`setState` updater, and React runs updaters during render, so an `onChange` that updates React state
— `router.push`, `router.replace` — logs:

```txt
Cannot update a component (`Router`) while rendering a different component
```

Pre-existing since `0.1.0`, and invisible until now because `apps/demo` writes to `window.history`,
which is not a React update. Found by building the Next.js example.

Workaround, applied in the example and documented in the guide:

```ts
queueMicrotask(() => router.push(href, { scroll: false }))
```

It is **not** fixed here because the fix moves `onChange` timing, which is the contract 80 hook tests
describe, and that is a design decision rather than a patch to make at the end of a release. It is
written up with its options in
[Sprint 1 task 6](../sprints/sprint-1/06-onchange-fires-during-render.md) and is the first item of
Sprint 2. `@filterbridge/browser`'s `pushUrlFilters` / `replaceUrlFilters` are unaffected.

## Infrastructure

- **`pnpm format:check` runs in CI**, as its own `format` job on Linux only — Prettier's output does
  not vary by platform. It follows one mechanical Prettier pass over 74 files, landed as a single
  commit and listed in `.git-blame-ignore-revs`.
- **`.gitattributes` pins every text file to LF.** The roadmap's "69 unformatted files" and the
  sprint plan's "122" disagreed because the second was measured on a Windows clone with
  `core.autocrlf=true`, where Prettier's `endOfLine: 'lf'` default flags every file on disk. The real
  number was 74. Without this, the new CI job would pass on Linux and be permanently red for any
  contributor on Windows.
- **Suite: 538 → 573 tests across 29 files.** The 538 from `0.2.0` pass unmodified — the guard on the
  key-derivation refactor.
- **`.smoke/` covers the new option** in both ESM and CJS, against the packed tarballs: custom keys
  round-trip, `getFilterParamKeys` reports them, `next` agrees with `core`, the DTO ignores them, and
  `defineFilters` throws on a collision. 60 ESM and 44 CJS assertions, all passing.

## Upgrading

```bash
pnpm add @filterbridge/core@0.3.0 @filterbridge/react@0.3.0
# and whichever adapters you use
```

No code change is required unless your schema has two filters resolving to the same URL param key,
which now throws at `defineFilters` and did not before. Everything else is additive.
